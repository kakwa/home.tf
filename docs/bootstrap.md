# Bootstrapping the homelab

How to go from a manually installed Proxmox VE host to working internal DNS + LDAP.
The AI server is a separate track. The legacy `terraform/` stack (libvirt/Talos) is not
part of this path.

```mermaid
flowchart TD
    C["Controller (this repo)"] --> B["1. bootstrap.yml<br/>limit: kvm"]
    B --> H["2. hypervisor.yml<br/>Proxmox VE + infra pool token"]
    H -->|infra@pve token| T["3. tofu/infra apply<br/>infra VMs + generated Ansible inventory"]
    T --> D["4. infra.yml --limit dns<br/>BIND + DNSCherry"]
    D --> L["5. infra.yml --limit ldap<br/>OpenLDAP + ldapcherry + SSH/LDAP"]
    L --> R["6. tofu/infra apply again<br/>RFC 2136 A records"]
    R --> G["7. infra.yml --limit registry<br/>certbot + Docker registry"]

    subgraph AI["Separate track: AI server"]
        A["ai / 192.168.1.20"] --> AB["bootstrap.yml --limit ai"]
        AB --> AP["ai.yml --limit ai"]
    end
```

Every playbook starts with a fact-less play running the `bootstrap` role, so a
fresh host is prepared automatically on first contact. The role writes a marker
at `/etc/ansible/bootstrapped` and skips all its work on later runs; the
explicit `bootstrap.yml` steps below are a thin wrapper around the same role
(plus the static-IP play) and are safe to re-run. Force a bootstrap again with
`-e bootstrap_force=true` or by removing the marker.

Order matters for two reasons:

- `tofu/infra` needs the `infra` API token created by the hypervisor play.
- The other infra VMs use the DNS VM as resolver, and DNSCherry needs LDAP for
  logins, so DNS comes before LDAP.

## Before you start

- Install the base OSes by hand; that step is not automated here:
  - Hypervisor (`kvm`): [Proxmox VE ISO](https://www.proxmox.com/en/downloads/proxmox-virtual-environment/iso).
  - AI server (`ai`): [Debian testing netinst ISO](https://cdimage.debian.org/cdimage/daily-builds/daily/current/amd64/iso-cd/debian-testing-amd64-netinst.iso).
- Clone with submodules: `git submodule update --init --recursive`.
- Have `ansible`, `tofu`, `sshpass` (for first password logins) and the
  `community.general` collection installed.
- Secrets are gitignored: `ansible/pve_pools/infra.token` is generated in step 2;
  the TSIG secret must match in `ansible/dns_tsig_secret.txt` and
  `tofu/infra/dns.auto.tfvars.json`; the `ansible/openldap_*.password.txt` files
  are generated on first use. OVH tokens are only needed for the certs on
  `ansible-master` (wildcard) and `registry` (`registry.int.kakwalab.ovh`).

## Steps

```sh
# 1-2. Hypervisor
cd ansible
ansible-playbook -k -K --limit kvm \
  -e "ansible_host=192.168.1.30" -e "ansible_user=kakwa" bootstrap.yml
ansible-playbook --limit kvm hypervisor.yml

# 3. Infra VMs (writes ansible/inventory/infra.yml)
cd ../tofu/infra
tofu init
tofu apply -var='dns_update_server='   # omit this flag if BIND is already up

# 4-5. DNS, then LDAP (one play; the pool roles are selected by inventory group)
cd ../../ansible
ansible-playbook --limit dns infra.yml
ansible-playbook --limit ldap infra.yml

# 6. Publish the RFC 2136 records now that BIND is running
cd ../tofu/infra
tofu apply

# 7. Registry node (after its DNS record is published)
cd ../../ansible
ansible-playbook --limit registry infra.yml
```

If `dns_update_server` is left empty, no DNS records are managed at all; the
plain `tofu apply` at the end is what creates them.

## AI server

Independent of the chain above: no Proxmox, no infra pool, no DNS/LDAP dependency.
Start from a manually installed [Debian testing](https://cdimage.debian.org/cdimage/daily-builds/daily/current/amd64/iso-cd/debian-testing-amd64-netinst.iso) host.

```sh
cd ansible
ansible-playbook -k -K --limit ai \
  -e "ansible_host=192.168.1.20" -e "ansible_user=kakwa" bootstrap.yml
ansible-playbook --limit ai ai.yml
```

## Short notes

- `ansible/inventory/infra.yml` is generated by step 3; never edit it by hand.
- A lost `pve_pools/*.token` cannot be recovered; delete the token in PVE and
  re-run `hypervisor.yml`.
- Known gap: `ssh_ldap` does not currently reuse the generated readonly LDAP
  password, so LDAP-backed SSH logins need that variable wired at play level.
